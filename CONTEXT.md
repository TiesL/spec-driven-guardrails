# Glossary — spec-driven-guardrails

Project jargon → meaning. Separate from `ARCHITECTURE.md`: that's about
structural decisions, this is about language. Optional and living — update
it as a new term arises or an existing one changes meaning, don't try to
make it complete in one go.

| Term | Meaning |
|---|---|
| NFR | Non-functional characteristic. One of the fifteen registered in `nfr/*.md`, each with a fixed `spec-*` question a project answers `yes`/`no` in `WORKFLOW-ADOPTION.md`. Distinct from the other, non-NFR entries in `CHANGES.md` (`proces-*`, `test-*`, `ci-*`, ...). |
| `spec-*` | The prefix reserved exclusively for the fifteen NFR entries — nothing else in `CHANGES.md` uses it. `pre-merge-review`'s scope keys on this prefix, so a non-NFR entry named `spec-*` would get wrongly swept into that review scope. |
| `Covers:` | The field, under a scenario heading in `TEST-SCENARIOS.md` (or an `AC<n>` in a GitHub issue), naming the `PRD.md` functionality (or scenario) it realizes — comma-separated tokens like `F3, S7`. Only the field counts as a reference; an ID mentioned in running prose doesn't. This is the mechanism behind traceability links 1 and 2. |
| Traceability link 1 | PRD functionality ↔ TEST-SCENARIOS scenario, both directions, checked offline by `check-traceability.sh` as part of `check` — no network, no `gh`. |
| Traceability link 2 | Scenario ↔ issue: every scenario in `TEST-SCENARIOS.md` must be named by at least one issue's `Covers:` field. Checked by `scenario-gate.sh`, run as part of `pre-merge-review` (not a local `check`, since it needs `gh`/network). |
| Traceability link 3 | PR ↔ issue: the PR that closes a work item must actually reference it (`Closes #N` in the PR title/body — a commit message alone doesn't count while the PR is open). Checked by `check-pr-issue-link.sh`, a **hard block in CI** (not fail-open) since `GITHUB_TOKEN` is guaranteed there. |
| Traceability link 4 | An issue's own shape: a work-item issue must carry an `AC<n>` heading and a `Covers:`/pre-migration `Dekt:` field; an epic's Work items list must name at least one real `#<n>`. Checked by `issue-structure-gate.sh`, run as part of `pre-merge-review` — the only one of the four links that looks at the issue itself rather than what points at it. |
| Adoption registry / `WORKFLOW-ADOPTION.md` | The per-project table recording, one row per `CHANGES.md` entry, whether that change applies here and why. `adopt.sh` seeds `yes`-default rows on first adoption with a provisional stamp; `pending-changes.sh` reports rows a project hasn't answered yet. |
| Substantiation | The requirement that a `yes` (or a changed `no`) in `WORKFLOW-ADOPTION.md` be backed by an objective reason recorded in `PRD.md`/`ARCHITECTURE.md` — not silently accepted. A row still carrying only the provisional adoption-time stamp is `[requires substantiation]`, which `pre-merge-review` treats as a review finding. |
| W-number | A sequential internal work-item identifier used in this repo's own `PRD.md`/`CHANGES.md` prose (e.g. "W19b", "W27") to trace a design decision back to the PR that built it — distinct from, and older than, this repo's later move to plain GitHub issue numbers for that role. |
| `F`/`S`/`R`/`T` ID prefixes | `F<n>` — a functionality heading in `PRD.md`. `S<n>` — a scenario heading in `TEST-SCENARIOS.md` (the letter is customary, not fixed — a project may use its own, e.g. `R`/`A`/`B`/`P`). `R<n>` — this repo's own original regression scenarios (issue #7). `T<n>` — this repo's own original traceability scenarios (issue #8). A trailing lowercase letter (`S2b`) or a two-letter prefix (`OP4`) are both existing usage, not sloppiness. |
| `AC<n>` | An acceptance criterion inside a GitHub issue (epic or work item), Given/When/Then, same notation as a `TEST-SCENARIOS.md` scenario but deliberately numbered differently — so a search for scenario references never also hits the issue defining its own criteria. |
| Epic / work item | The two GitHub issue templates (`templates/ISSUE_TEMPLATE/`) work is split into. An epic names its scope and links its work items (human-readable "Work items" checklist); a work item names its epic via a `**Epic:** #<n>` field (the one machine-trusted signal — see "epic auto-close" below) and carries its own `Covers:`/acceptance criteria. |
| Fail-open / fail-closed | A guard's behavior when it can't verify something (no `gh`, no network). Fail-open (the default almost everywhere in `hooks/git-guardrails`) lets the command through with a loud warning — "when in doubt, allow," since a false-positive block reaches every adopted project at once. Fail-closed is the deliberate exception for CI's link-3 hard block and `check-main-via-pr.sh`, where `GITHUB_TOKEN` is guaranteed and silence would mean "nothing wrong" while actually meaning "couldn't check." |
| The merge guard | `hooks/git-guardrails`' block on `gh pr merge`: refuses without the pre-merge-review marker, and separately refuses if CI isn't green. Fails open without `gh`/network, same rule as everywhere else. |
| The pre-merge-review marker | `<!-- pre-merge-review:done sha=<commit sha> -->`, posted on its own line in the findings comment the `pre-merge-review` skill leaves on a PR — never paraphrased. Sha-pinned to the reviewed commit (issue #225): the merge guard requires a marker matching the PR's *current* HEAD, so a commit that lands after review needs a fresh one. |
| Technical debt table | The `## Technical debt` section in `PRD.md`: a review finding that isn't fixed before merge lands here instead of disappearing — what it is, why it's acceptable for now, and the concrete trigger that means it needs addressing after all. |
| Epic auto-close | The mechanism (`epic-auto-close.sh`, on the `issues: closed` GitHub Actions event) that closes an epic once every issue naming it via `**Epic:** #<n>` is itself closed — keyed on that field, not the epic's own "Work items" checklist, which is for humans and can drift. |
